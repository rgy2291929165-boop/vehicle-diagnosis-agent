# ADR-001：第五周充电维护辅助场景

日期：2026-10-16；适用阶段：第 5–6 周。

状态：范围方案与学习者理解验收已通过（2026-10-17）；本 ADR 中的新业务行为尚未实现或验收。

编写：教练按学习者“请你帮我完成”的要求代写。唯一代码主项目为 `/Users/jzr/Desktop/vehicle-diagnosis-agent`，study 同名目录只承载本阶段规划记录，不同步代码。

## 1. 背景、用户与目标

目标用户为遇到充电状态或警报问题的车主，以及协助记录问题的服务受理人员。系统先帮助用户理解适用资料，再按明确需求形成可供人工复核的处理请求。

现有主项目已经分别实现检索、只读工具、checkpoint、人工审批和幂等工单，但诊断 HTTP 接口仍使用规则选择工具，各模块尚未组成统一业务任务。D1 已由学习者完成一次真实模型回答烟测，单次耗时 2.075 秒；该结果只证明一条模型回答路径可用。

第五周目标是在有限场景中贯通“补问→证据回答→按需生成草稿→人工审批→自建工单提交”，每个结论和写入动作都能追溯。第六周在同一范围内比较单 Agent 与有边界的多 Agent。

## 2. 场景决定

| 场景 | 用户输入示例 | 允许输出 | 初始本地证据 |
|---|---|---|---|
| S1：充电口状态灯解释 | “我的 2024 年北美版 Model 3 充电口灯红色，是什么意思？” | 按适用资料解释状态、引用完整片段；资料允许时提示查看进一步警报，不从灯色推断具体损坏部件 | `w2-tesla-charge-status` |
| S2：充电警报解释与处理请求 | “我的 2024 年北美版 Model 3 显示 CP_a054，充电受限，想请人工协助处理。” | 按适用资料解释警报及明确支持的限制；区分资料描述与已确认原因；用户有处理需求时收集必要信息并生成待审批草稿 | `w2-tesla-charge-alerts` |

S1 知识回答可以直接结束。S2 也允许只解释警报后结束；只有用户明确请求报修、人工协助或同意发起处理请求时才进入工单分支。

选择理由：两个场景已有可定位的资料摘要，覆盖从信息解释到人工处理的连续需求，能够验证证据、模型决策与审批边界；相比直接诊断绝缘故障，更符合当前资料能力。

## 3. 证据与适用范围

| 文档 | 本地主项目位置 | 当前 metadata 标注 |
|---|---|---|
| 状态灯 | `data/documents/w2-tesla-charge-status.json` | Model 3 Owner Manual 2024+，North America；retrieved 2026-09-14；官方英文页面的中文意译摘要 |
| 警报 | `data/documents/w2-tesla-charge-alerts.json` | Model 3 Owner Manual 2024+，North America；retrieved 2026-09-14；官方英文页面的中文意译摘要 |

这些是本地摘要的元数据声明，不是针对所有车型、地区、软件版本的兼容性证明，也不是厂家维修工序。当前记录没有固定手册修订号或车辆软件版本，不能据此声称已验证全部 2024+ 车辆。

D2 须复核原始来源、章节、车型/年份/地区、获取日期和摘要准确性，记录可复现来源；必要时补充更精确版本或缩小适用范围。原始 URL 已存在各 JSON 的 metadata.source 中，本 ADR 不声称本轮重新核对过源网页。

第二周冻结语料与题集保持历史用途；第五周新增资料和开发场景单独版本化，不通过改动旧冻结资料使新任务“命中”。后续回答引用使用真实输入片段 ID，而不是仅列文档名称。

## 4. 输入、补问与无证据处理

- 个性化资料判断需要车型、年份、地区，以及用户观察到的状态灯/症状或警报原文。只有缺失项会影响当前回答时才补问，不一次要求所有字段。
- 一般性问题可以明确按资料限定范围回答，不必索取真实 VIN。用户问“我的车”却没有足够适用信息时，先询问车型/年份/地区，不能默认是北美版 Model 3。
- `symptom`（症状）、充电灯状态、厂家 `alert_code`（如 CP_a054）和标准 `dtc_codes`（如 P0AA6）分开表达。纯灯色或警报问题不强制提供 DTC，也不伪造故障码填充接口。
- 创建处理草稿前，需要稳定的自建车辆/资产标识、用户报告、处理意图以及已知警报等必要信息；测试可使用明确标注的模拟标识，无须采集真实 VIN 才能演示。
- 来源不适用、检索无充分证据或关键主张无法支撑时，清楚说明缺口并进入本地人工复核状态。P0AA6 目前缺少真实证据，保留为无证据案例，不生成具体维修结论。
- “转人工”在本阶段指保存待复核材料和状态，不代表已通知真实维修人员，也不自动创建正式工单。

## 5. 流程与权限

```text
用户问题 → 适用性/必要信息核对 → 必要时补问 → 只读证据查询
  → 有证据：带引用解释；无证据：说明缺口并标记待人工复核
  → 无处理需求：结束
  → 有明确处理需求：补齐必要字段 → 生成待审批草稿
  → 人工 approve / edit / reject
  → 有效批准且内容未变化：确定性服务幂等提交 → 返回自建工单编号
```

| 主体 | 可以做什么 | 边界 |
|---|---|---|
| 模型/Agent | 提出只读查询、整理证据、解释资料、说明缺口、建议或生成处理草稿 | 无权授予权限、批准草稿或直接写正式工单；第六周 Review 也不能替代真人批准 |
| 确定性服务 | 校验工具允许列表、参数、调用预算和状态；执行只读工具；从受控状态读取批准记录并提交 | 模型输出不构成授权；正式提交须匹配有效批准内容，重复提交返回同一业务结果 |
| 人工审核者 | approve、edit、reject；审阅资料、用户报告与待提交内容 | edit 后继续待审批，必须再次明确批准；reject 不提交 |

写入只由服务在有效人工批准后执行。批准与提交保持可区分，保存被批准内容及审计记录；批准后内容发生变化时不得沿用旧批准。服务端身份与角色授权的完整实现按第七周路线安排，本 ADR 不把当前本地交互批准描述为已接入企业身份系统。

## 6. 现有代码差距与实施影响

- `app.agent_api` 当前是单次只读接口，无任务生命周期；`requested_tool` 来自请求，尚非模型自主选择。D3–D5 逐步落实新契约、受控模型选择和任务 API。
- 当前完整性检查、`build_work_order_draft` 和工单存储都要求非空 DTC；这与纯状态灯/厂家警报场景不一致。D3 必须明确区分输入类型及草稿契约，后续同步调整相关校验和测试，不能为了复用旧接口而编造 DTC。
- 当前诊断图只检索包含完整 DTC 的片段；S1/S2 需要支持适用性约束下的症状/警报资料检索路径。CP_a053/CP_a054 不能当作 P0AA6 模拟目录已有记录；未知查询必须如实失败或绕过不适用的工具。
- 继续复用 Python、FastAPI、Pydantic、LangGraph、BM25、MCP、SQLite 与已验收审批/幂等逻辑；本阶段不引入第二套 Agent 框架或提前迁移数据库。
- 若上述契约调整超出日预算，延长当前学习日；不删减内容变更后重新批准、无证据和重复提交的验收。

## 7. 暂不覆盖与来源分类

不覆盖高压拆装维修、根据症状自动确认部件损坏、设备控制或自动维修；不把多 Agent 一致意见当作故障事实。不扩展到缺少适用资料的车型、地区或警报。

| 来源/效果 | 本阶段标注 |
|---|---|
| 车主手册本地摘要 | 有官方出处的中文意译，适用性与更新情况待 D2 复核 |
| 模型调用 | 真实托管百炼 API；请求别名、Prompt 与运行证据记录，未知费用/快照不填猜测值 |
| DTC、车辆历史、库存工具 | mock 数据；MCP 传输真实不改变数据为模拟的事实 |
| 工单服务 | 自建 SQLite 业务写入，非外部企业维修系统 |
| 车辆输入/设备 | 开发案例可为模拟用户输入；本 ADR 无实车采集或真实设备诊断证据 |

## 8. 后续验收案例

以下为拟定开发案例与预期行为，均尚未运行；不计入已通过测试或准确率。

| 类型 | 输入/前提 | 预期结果 |
|---|---|---|
| 正常资料回答 | “2024 年北美版 Model 3 充电口灯红色是什么意思？”且资料适用 | 返回摘要直接支持的解释与输入片段引用；不归因到具体零件，不强制 DTC，不建工单 |

| 编辑/拒绝/重复提交 | 草稿生成后分别编辑、拒绝；另一分支批准后同键提交两次 | 编辑后仍待批准；拒绝不写入；有效批准分支两次提交仅形成一条自建工单 |

## 10. 2026-10-17 理解确认

学习者回答“因为无法确定具体的故障问题、来源”，正确识别缺乏故障码依据。教练补充：保留真实观察与缺失字段，故障码应来自可追溯的用户/设备报告，不能以虚构值满足接口。D1 文档与理解验收通过，开始 D2 来源核对；本文业务功能与拟定案例仍待后续实现和运行。
