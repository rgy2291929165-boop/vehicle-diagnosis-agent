# 第四周：正式工单存储与幂等提交

- 负责人：学习者与教练；前置为草稿、审批规则、审批图及跨进程 CLI 已实现且测试通过，现有全量基线 169 passed。学习者尚未在本轮提供上一项 CLI 的运行输出。
- 目标：在独立 submit 命令中读取持久化审批结果，将批准内容写入本地 SQLite work_orders 表；不在审批节点内增加写入副作用。
- 接口：app.work_order_store.create_work_order_once(state, *, idempotency_key, database_path)。state 来自审批图的 checkpoint。
- 提交条件：状态与草稿均为 approved；最后一次记录为有效 approve，且记录中的草稿与当前内容一致。未批准、已拒绝、批准后内容被改动或缺少批准记录均拒绝写入。
- 表字段：work_order_id（UUID）、idempotency_key（UNIQUE）、status（open）、approved_draft_json（已批准草稿的完整快照）。保留批准内容，不在保存时改变文本。
- 幂等：先在事务中尝试插入，数据库唯一约束处理重复键；相同内容返回已有记录，不同内容报错且不覆盖。JSON 键排序消除字典键顺序的影响。
- CLI 使用 work-order:<thread_id> 作为幂等键；同一会话为同一工单请求，连接同一工单库时请求 ID 应唯一。重试始终使用同一工单库和 thread_id。
- 默认工单库：data/work_orders/work_orders.sqlite；与审批 checkpoint 分开。启动/修改/批准/拒绝不会创建工单库，只有 submit 写入。
- 选择：独立提交易于区分业务审批与持久化，也便于在提交进程未返回结果时重试；此步不增加审批图写入节点或分布式事务。
- 验收：批准前与拒绝后不写入；修改需再批准；保存内容与批准一致；同键同内容、同键不同内容、不同请求、并发重试、提交后进程退出再重试。
- 定向命令：python -m pytest tests/test_work_order_store.py -q。
- 演示：start → edit（可选）→ approve → submit → 再次 submit；两次提交的正式工单编号应一致，表中只保留一条该幂等键记录。
- 边界：这是固定教学车辆的本地工单表，尚未对接企业工单系统，也不代表真实维修诊断正确性。暂未自动修改已提交工单；后续故障注入、转人工、MCP 和部署仍待验收。

- 定向 20 passed；全量 189 passed（API 文档导入测试隔离到临时目录）。
